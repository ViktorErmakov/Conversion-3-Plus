# Conversion 3 Plus — описание проекта для ИИ

Расширение `Conversion_3_Plus` для типовой конфигурации **Конвертация данных 3.1**.
Встраивает консоль кода (макет `bsl_console`) в формы обработчиков правил обмена в пользовательском режиме: подсветка, темы, подсказки по метаданным источника/приёмника, замена вхождений. Runtime платформы: **8.3.24+**, рекомендуется **8.3.27+** (текст HTML-макета в поле, без `file://`). Совместимость расширения: `8.3.10`.

Публикация: https://infostart.ru/public/1289837/
Префикс расширения: `Расш1_`. Назначение: `Customization`.

## Жёсткое правило: MCP обязателен

Любая работа по этому репозиторию (ответ, план, правка кода, разбор ошибки) выполняется **только** через MCP:

| Сервер | Namespace | Зачем |
|---|---|---|
| 1C:EDT | `user-EDT MCP Server` | Метаданные, модули, формы, ссылки, диагностика, правка BSL |
| v8std.ru | `user-v8std` | Стандарты BSL/SDBL, диагностики АПК/BSLLS/EDT, проверки правок |

Если EDT или v8std недоступны (`namespaceStatus` не `ready`, ошибка discovery, нет инструментов кроме `mcp_auth`):

1. Не отвечать по существу.
2. Написать: серверы MCP недоступны, их необходимо запустить.
3. Для EDT сначала вызвать `mcp_auth`, затем повторить discovery. Если снова ошибка — остановиться.

Нельзя подменять EDT чтением `.xml` / `.mdo` / `.bsl` с диска «на глаз», когда сервер недоступен. Диск — вспомогательный источник после EDT.

## Что делает расширение

На формах обработчиков программно создаёт HTML-консоли вместо обычных текстовых полей алгоритмов.

Типовой цикл формы:

1. `&После` `ПриСозданииНаСервере` — `Расш1_КонсольКода.СоздатьКонсоль` для полей алгоритмов **только своего типа конвертации**.
2. `&После` `ПриОткрытии` / смена страницы — `Расш1_КонсольКодаКлиент.НазначитьРеквизитуКонсолиАдрес` (лениво копирует текст HTML из кэша формы).
3. События HTML: `Расш1_Подключаемый_КонсольДокументСформирован` / `Расш1_Подключаемый_КонсольПриНажатии` → фасад `Расш1_КонсольКодаКлиент`.
4. `&После` `ПередЗаписью` — `Расш1_КонсольКодаКлиент.ЗаписатьТекстыКонсолейВОбъект`.
5. Команды консоли: одна `Расш1_Подключаемый_КомандаКонсоли` (тема, замена вхождений, направление «отправка» / «получение»).

Подсказки по метаданным не работают, пока на форме релиза не выполнена команда `Расш1_ОбновитьОписаниеМетаданных` (`Расш1_КоллекцияМетаданных.ОбновитьОписаниеМетаданных`). Описание строится запросами из макетов справочника `Объекты` и кладётся в JSON для консоли.

Консоль кода на формах **не запускать**, если тип конвертации не тот, для которого пишется код.

## Документация консоли кода (bsl_console)

**Жёсткое правило: саму консоль не менять.** Встроенная HTML-консоль — сторонний [salexdv/bsl_console](https://github.com/salexdv/bsl_console) (ветка `webpack`). Её только **используем** через документированный API (`defaultView`, `eventData1C`). Запрещено править HTML/JS/CSS редактора, общий макет `bsl_console`, патчить сборку и дописывать поведение «внутри» консоли. Сборка `npm run build:pack` кладётся в `vendor/bsl_console/index.html` и в макет как **текст**. Нет нужной функции в API — менять обёртки расширения или отказаться от фичи, а не исходники консоли. Редактор один — `bsl_console`.

Любая задача про консоль, JS-API редактора, события HTML, темы, поиск/замену, метаданные для автокомплита, сниппеты, режимы языка **обязана** опираться на эту документацию, а не на догадки и не на устаревший код расширения.

Источник правды:

- README: https://github.com/salexdv/bsl_console — таблицы функций взаимодействия с 1С и событий редактора
- Постраничные описания: https://github.com/salexdv/bsl_console/tree/webpack/docs
- Конкретная функция/событие — страница `docs/<имя>.md` (например `update_metadata.md`, `get_metadata_event.md`, `init.md`, `set_text.md`)

Перед правкой `Расш1_КонсольКода*`, `Расш1_КоллекцияМетаданных` и обработчиков `Расш1_Подключаемый_Консоль*`:

0. **Сначала конвертация.** Если задача про подсказки после `Справочники.` / `Документы.` — проверить, что `Форма["Конвертация"]` заполнена. Пустая ссылка → нет релизов → пустой JSON → только встроенные имена вроде `ТипВсеСсылки`. Пока это не подтверждено, запросы, JSON и разбор `EVENT_GET_METADATA` не менять. Формы не трогать, пока отдельно не сказано.
1. Найти в README нужную функцию или событие.
2. Прочитать соответствующий `docs/*.md` (сигнатура, JSON, события, ограничения платформы).
3. Использовать **все** возможности консоли, которые нужны задаче Conversion 3 Plus (текст, выделение, темы, метаданные, `EVENT_GET_METADATA`, поиск, режимы `bsl` / запрос, сниппеты и т.д.), через штатный API, а не урезанный самодельный набор вызовов и не правкой консоли.
4. Не выдумывать имена JS-функций и формат JSON. Если в репозитории консоли API изменился — брать новую сигнатуру из docs, затем править **только** обёртки расширения.

Платформа консоли в апстриме — не ниже 8.3.24 (для 8.3.27+ single-file HTML). Совместимость расширения КД (`8.3.10`) не отменяет чтение docs: ограничения платформы смотреть там же.

## Два контура КД 3: XDTO и XML

В КД 3.1 это **два разных продукта внутри одной конфигурации**. Различаются типом `Справочник.Конвертации.ТипКонвертации` (`Перечисление.ТипыКонвертаций`: `XDTO` / `XML`) и предопределёнными группами `Конвертации.ФорматXDTO` / `Конвертации.ФорматXML`.

На формах флаги: `КонвертацияXDTO`, `ЭтоКонвертацияXDTO`. Страницы: `СтраницаКонвертацияXDTO` / `СтраницаКонвертацияXML`, `ОбработчикиСобытийXDTO` / `ОбработчикиСобытийXML`.

**Запрещено** смешивать контуры в одном плане, одном списке задач и одном наборе правок. Перед работой явно зафиксировать контур. Общие модули консоли (`Расш1_*`) трогать только если изменение нужно обоим контурам и это сказано отдельно.

Подробности обработчиков, модулей и покрытия — в правиле `.cursor/rules/xdto-и-xml.mdc`.

## Как работать через EDT

Порядок на задачу:

1. Проверить `get_server_status` и `list_projects`. Оба рабочих проекта в `ready`.
2. Зафиксировать контур: **XDTO** или **XML**.
3. Найти объекты: `get_metadata_objects` / `get_metadata_details` / `list_modules`.
4. Смотреть код: `get_module_structure`, `read_module_source`, `read_method_source`. Не читать модуль целиком с диска, пока EDT не отдал структуру.
5. Связи: `find_references`, `get_method_call_hierarchy`, `search_in_code`.
6. Новые заимствования из типовой — только `adopt_metadata_object` (базовый проект `Конвертация_данных_31_демо`, `extensionProjectName` = `Конвертация_данных_31_демо.Conversion_3_Plus`).
7. Правка BSL — инструменты EDT (`write_module_source` и аналоги), не «тихая» правка файла в обход модели.
8. После правки: `revalidate_objects` / `get_project_errors`. Коды проверок разобрать через `v8std_explain_diagnostics` и `v8std_get_page`.
9. Незнакомый инструмент EDT — сначала `get_tool_guide`.

Для стандартов: `v8std_search` (проза), `v8std_explain_snippet` (фрагмент BSL), `v8std_explain_diagnostics` (коды), затем `v8std_get_page` / `v8std_get_related`.

Ключевые стандарты: структура модуля `#std455`, описание процедур `#std453`, префикс расширения `v8cs:extension-method-prefix` / `extension-md-object-prefix` / `extension-variable-prefix`, подключаемые обработчики `#std492`.
